## 1. Guiding Principles (Carried Forward From the Master Spec)

Before any framework or hosting decision, three constraints from the master spec shape everything in this volume:

1. **No web scraping, ever.** All external sports/odds data flows through one internal Sports Intelligence Layer. Nothing else in the system talks to a provider directly.
2. **Nothing is a black box.** Every recommendation must be reconstructible months later (Time Machine requirement). This is an architecture requirement, not just a data requirement — it means snapshotting, not just logging.
3. **The AI Orchestrator must be able to swap models without a redesign.** OpenAI and Claude are both in play today; whatever routes between them can't hardcode either one as "the" model.

Everything below is built to satisfy these three constraints first, convenience second.

### 1.1 Core Architecture Principles (v4.0)

Ten principles, added as the explicit lens for future architectural decisions rather than leaving that judgment implicit across five volumes. Several are restatements of decisions already made elsewhere — collected here so a future decision can be checked against a short list instead of re-deriving the reasoning from scratch each time:

1. **Download once, reuse everywhere.** Never repeatedly call an external API for the same information — store it in Supabase, read from there. (Already the entire reason the Sports Intelligence Layer and Redis cache exist, §8.)
2. **Background workers gather data; the AI does not collect raw data during a user request.** Every agent reasons over already-assembled intelligence (`daily_game_intelligence`, Volume 3 §4.1), never over a live external API call mid-request.
3. **AI reasons, workers gather.** A clean separation of responsibility — an agent's job is judgment, not fetching.
4. **Store intelligence, not just raw data.** The derived score tables and `daily_game_intelligence` (Volume 3 §4.1–§4.2) exist because precomputed judgment is more valuable than a pile of numbers an agent has to re-derive every time.
5. **Every recommendation must be explainable.** (Volume 4 §8 — already load-bearing.)
6. **Everything must be observable.** (§9's per-component latency tracking, error tracking, health checks.)
7. **Every recommendation must be reproducible.** (Volume 3's Time Machine principle — the project's oldest and most-repeated constraint.)
8. **Optimize for scalability** — but not prematurely. This principle and #10 below are in tension on purpose; #10 wins at MLP stage.
9. **Optimize for user trust** over engagement, win rate, or any other metric that could conflict with honesty (Volume 1 §1's core tension).
10. **Keep Phase 0 intentionally focused.** Scalability work for sports that aren't NFL, features without a proven MLP-stage consumer, and infrastructure without a proven need all get deferred — not because they're bad ideas, but because building them now is the more expensive time to build them wrong. This is the same reasoning that's driven every deferral logged in this changelog so far (Knowledge Graph, Public Transparency Portal, the bulk of the ~150-table proposal, sportsbook promotions, social sentiment).

## 2. Backend Framework: FastAPI vs. Node.js

**Recommendation: FastAPI (Python).**

The master spec asked for this decision to be justified, not assumed, so here's the actual tradeoff analysis rather than a default.

| Factor | FastAPI (Python) | Node.js | Winner |
|---|---|---|---|
| AI/ML ecosystem | Native — OpenAI SDK, Anthropic SDK, numpy/pandas/scikit-learn all first-class, needed later for the Continuous Learning Engine's calibration work (Volume 4) | Workable via SDKs, but numerical/ML work means shelling out to Python anyway eventually | **FastAPI** |
| Async I/O performance | Excellent (async/await native, ASGI) — comparable to Node for concurrent API calls to multiple providers/agents | Excellent, this is Node's home turf | Tie |
| Data validation | Pydantic gives you schema validation and type safety for free on every request/response — directly useful for the Explainability Engine's structured outputs | Requires a separate library (Zod, etc.) bolted on | **FastAPI** |
| Team familiarity / hiring | Slightly smaller talent pool than Node, but growing fast in AI-adjacent hiring | Larger overall pool | Node (minor) |
| Supabase/Twilio SDK support | Good, well-maintained Python clients | Slightly more mature JS clients (Supabase's JS SDK is the primary one) | Node (minor) |

**Why FastAPI wins overall:** This platform's hardest engineering problems — orchestrating multiple AI agents, calibrating confidence scores, running the adaptive weighting system, eventually training/fine-tuning components of the Continuous Learning Engine — are all Python-native problems. Node would work for the CRUD/API surface, but you'd end up standing up a second Python service for the ML-heavy parts anyway (agent evaluation, calibration, weighting), which means two languages, two deploy pipelines, and a network hop between them for no real gain. Better to commit to one stack that's strong everywhere the hard problems live, and accept a marginally smaller frontend-adjacent talent pool as the tradeoff.

**What this decision does NOT mean:** the frontend stays Next.js/React regardless (Volume 5) — this is a backend-only decision. FastAPI serves a clean REST/JSON API; the frontend doesn't know or care what language generated it.

```
                              └───────────────────────┘
```

Four service types, all deployed on Railway (Section 5):

1. **API Gateway** — the only thing the frontend ever talks to. Handles auth, rate limiting, request routing to internal engines.
2. **AI Orchestrator service** — stateless compute that fans out to the agent committee, runs the consensus engine, and returns a recommendation package. Detailed in Section 7.
3. **Sports Intelligence Layer** — the adapter layer to external providers (Section 8). Nothing outside this service ever calls a provider directly.
4. **Background workers** — long-running or scheduled processes: market monitoring, postgame review generation, agent weight recalculation, notification dispatch.

## 4. Service Breakdown

### 4.1 API Gateway (FastAPI)
Owns: authentication, request validation, rate limiting, routing to internal engines, response shaping. This is deliberately kept thin — it should not contain business logic. Its job is traffic control, not decision-making.

### 4.2 AI Orchestrator Service
Owns: model routing decisions, agent fan-out, consensus resolution, confidence gating, explainability packaging. This is the most complex service in the system and gets its own full treatment in Volume 4 — this volume only defines its *deployment shape* (stateless, horizontally scalable, no persistent state between requests beyond what's written to Postgres).

### 4.3 Sports Intelligence Layer
Owns: provider adapters (odds, stats, weather, injuries, rosters, schedules), normalization into one internal data model, caching to avoid redundant provider calls. Detailed in Section 8.

### 4.4 Background Workers
Owns: anything that runs on a schedule or reacts to an external event rather than a user request — market monitoring (continuous), postgame review generation (triggered by game completion), agent weight recalculation (scheduled, e.g. weekly), notification dispatch (event-triggered).

**Recommendation Worker (v4.0).** Previously, a recommendation only existed once a user asked for one — the flow was strictly on-demand: user request → Orchestrator → response. This adds a proactive path: `Master Refresh (Volume 3 §4.1) → Recommendation Worker → AI Committee (Volume 4 §2) → store recommendations`, running shortly after each Master Refresh so that a recommendation already exists by the time a user opens the app, rather than being computed live in front of them. **This coexists with, not replaces, on-demand generation** — the NL Engine (Volume 4 §7) can still trigger a fresh Orchestrator run for a specific request (e.g., "build me something around Mahomes") that the proactive worker wouldn't have anticipated. Documented here and in Volume 4 §3.1, since both the trigger (this volume) and the reasoning it triggers (Volume 4) need to agree on the flow.

**Why separate workers from the API Gateway:** Market monitoring in particular needs to run continuously regardless of whether any user has an active request in flight. Bundling that into the request/response API service would mean either blocking user requests or building ad-hoc background threading inside a service that's supposed to be stateless and horizontally scalable. Keeping workers separate lets each piece scale independently — you might need ten API Gateway instances during Sunday NFL traffic but only one market-monitoring worker running continuously.

### 4.5 Scoped Internal Event System (v2.0)

Added per the external architecture review, deliberately scoped down from the review's original proposal of a full event-driven architecture connecting every service. **At MLP stage, this uses Postgres LISTEN/NOTIFY** — no new infrastructure, since Supabase already provides it — rather than a dedicated message broker.

**Events implemented at MLP stage:**
- `RecommendationCreated`
- `RecommendationUpdated`
- `RecommendationWithdrawn`
- `GameFinished`
- `AgentWeightsUpdated`

**Events deferred to post-MLP** (real value, but no independent consumer exists yet at MLP scope): `GameStarted`, `InjuryUpdated`, `WeatherChanged` (the Market Monitoring worker's own internal logic can stay synchronous until multiple independent consumers need to react to these), `UserSubscribed`, `OCRCompleted` (both tied to features that are themselves post-MLP or early-MLP-adjacent per the Engineering Roadmap).

**Why scoped instead of full event-driven architecture:** a message broker and event schema versioning system is real operational weight this project's small-team, MLP-first strategy (Volume 1 §9) argues against front-loading. The scoped version delivers concrete value immediately — `RecommendationCreated`/`Updated`/`Withdrawn` directly power the Recommendation Timeline component (Volume 5 §4.2) — without the footprint of infrastructure that doesn't have proven consumers yet. If volume ever justifies it, migrating from LISTEN/NOTIFY to a dedicated broker (Redis pub/sub, or a proper queue) is a contained upgrade, not a rearchitecture, since the event *contracts* (names and payloads) don't change, only the transport.

**Where it plugs into the architecture diagram above:** the Background Workers box both publishes events (Market Monitor → `RecommendationWithdrawn`, `GameFinished`) and the API Gateway/frontend subscribes to a subset (`RecommendationUpdated`, `RecommendationWithdrawn`) via Supabase Realtime, which is what Volume 5 §2 already established as the mechanism for live dashboard updates — this section is the source of those events, not a separate system from what Volume 5 assumed.

## 5. Railway Deployment Strategy

**Environments:** `dev`, `staging`, `production` — three separate Railway environments, not just branches within one. This matters specifically because of the Time Machine requirement (Volume 1, principle 2): staging needs to be able to test against real provider data without any risk of a staging recommendation snapshot polluting the production reproducibility record.

**Official environment data-source policy (v4.0)** — this was previously only an informal note in the Engineering Roadmap's Phase 1 testing section; formalized here as the volume that actually owns environment strategy:

| Environment | Data Source | Users |
|---|---|---|
| **Development** | Sandbox APIs where the provider offers them, fake/seeded data otherwise | None — internal only |
| **Staging** | Real APIs, real odds, real schedules — mirrors production behavior | Internal testers only |
| **Production** | Real APIs, live traffic | Real customers |

Staging exists specifically to catch problems with real data before customers see them — using fake data in staging would defeat that purpose, and using real data in dev would burn API quota and provider rate limits on rapid, throwaway iteration. Each environment's data policy should be enforced at the adapter configuration level (§8), not left as a convention a developer has to remember when switching environments.

**Services per environment (Railway project structure):**
- `api-gateway`
- `ai-orchestrator`
- `sports-intel-layer`
- `worker-market-monitor` (always-on)
- `worker-recommendation` (v4.0 — proactive generation, §4.4)
- `worker-scheduled` (cron-triggered: postgame review, weight recalc)
- Supabase is *not* hosted on Railway — it's a separate managed service (Section 6, Volume 3 owns schema)

**Scaling approach:** Start with Railway's autoscaling on `api-gateway` and `ai-orchestrator` (these see traffic spikes tied to game schedules — Sunday NFL windows will dwarf a random Tuesday). `sports-intel-layer` and workers can run on fixed, smaller instances at launch since their load is more predictable (polling intervals, not user-driven spikes).

**Why Railway over raw AWS/GCP at this stage:** Railway's git-push deploys and built-in environment management dramatically reduce DevOps overhead for a small team, which matters when the same person or a very small team is wearing the product, business, and engineering hats simultaneously. This is the right tradeoff for launch and the first 6–12 months. Flag now, for a future major-version decision: if the platform reaches a scale where Railway's pricing or infrastructure control becomes limiting (hundreds of thousands of users, per the master spec's scalability target), migrating the containerized services to AWS ECS/Fargate is a straightforward move *because* everything is already containerized — this is a reason to keep Dockerfiles clean and provider-agnostic from day one rather than leaning on Railway-specific magic.

## 6. API Strategy

**Versioning:** All routes under `/v1/`. No exceptions, even for internal-only endpoints — this habit prevents painful breaking changes later once the frontend and any future mobile apps depend on a stable contract.

**Authentication:** Supabase Auth issues JWTs; API Gateway validates on every request. Service-to-service calls (Orchestrator → Sports Intel Layer, workers → Orchestrator) use a separate internal service token, never the user's JWT, to keep the blast radius of a leaked internal token limited to internal services.

**Rate limiting:** Tiered by subscription level (Volume 1, Section 2) — Free tier gets the tightest limits, Elite the loosest, enforced at the Gateway before a request ever reaches the Orchestrator. This double-serves as cost control on AI API spend, since Free-tier users are the least monetized but could otherwise generate the same compute cost as Elite users.

**Key endpoint groups:**
- `/v1/recommendations` — current recommendations, filtered by sport/user
- `/v1/recommendations/{id}/explain` — full explainability payload for one recommendation
- `/v1/recommendations/{id}/snapshot` — Time Machine reconstruction endpoint
- `/v1/chat` — natural language interface entry point (routes to NL Engine, Volume 4)
- `/v1/betslip` — optional OCR upload
- `/v1/user/profile`, `/v1/user/betting-dna`
- `/v1/webhooks/twilio` — inbound SMS
- `/v1/webhooks/provider/*` — inbound provider push notifications where supported (injury alerts, line movement), reducing reliance on polling

**Webhooks over polling where possible:** For providers that support push (injury news, breaking line movement), prefer webhooks into the Market Monitoring worker over constant polling — cheaper, faster, and reduces the chance of hitting provider rate limits during high-traffic windows like Sunday mornings.

## 7. AI Orchestration Architecture

This is a deployment-shape overview; full agent-level detail belongs in Volume 4. What belongs here is *how the orchestrator is deployed and structured as a service.*

**Model routing:** The Orchestrator holds a routing table (stored in Postgres, not hardcoded) mapping task type → preferred model → fallback model. This satisfies the master spec's "swap models without redesign" requirement — updating the routing table is a data change, not a deploy.

**Execution pattern:** Agent fan-out is async and parallel — all ~20 committee agents (Volume 4 defines the full list) execute concurrently against the same game snapshot rather than sequentially, since they're independent analyses. This is a hard requirement for latency: sequential execution of 20 agents, each making an LLM call, would make the natural-language chat interface feel unusably slow.

**Consensus + confidence gating:** After fan-out completes, the Consensus Engine runs as a synchronous step against all agent outputs. If aggregate confidence falls below threshold, the Orchestrator returns "No Bet Today" rather than publishing a low-confidence recommendation — this is where Volume 1's core principle #1 becomes actual code, not just philosophy.

**Cost/latency/quality balancing:** The routing table should weight this explicitly per subscription tier (tying back to Volume 1's Elite "priority agent compute" feature) — Elite tier requests can afford a slower, higher-quality model pass or a second reasoning pass on disagreement; Free/Pro tier requests use faster/cheaper routing by default. This needs a concrete metric to avoid becoming vague marketing language: recommend defining "priority compute" as Elite requests get a mandatory second-pass reconciliation step whenever agents disagree beyond a defined variance threshold, while Pro/Free accept the first-pass consensus. Volume 4 should finalize the exact threshold.

## 8. Sports Intelligence Layer & Provider Adapter Pattern

**Adapter pattern, strictly enforced:** Each external provider (odds, stats, weather, injuries, rosters, schedules) gets its own adapter implementing a shared internal interface. No other service — not the Orchestrator, not any agent, not any worker — ever imports a provider SDK directly. They only ever talk to the Sports Intelligence Layer's normalized internal models.

**Why this matters practically, not just architecturally:** Odds and sports data providers get acquired, change pricing, throttle limits, or degrade in quality more often than most external APIs. If provider-specific code is scattered across the Orchestrator and agents, replacing a provider becomes a system-wide hunt-and-replace. With the adapter pattern, replacing a provider means writing one new adapter that implements the existing interface — nothing upstream changes.

**Multi-provider strategy (per master spec):** Separate providers per data category rather than one all-in-one provider, specifically so a problem with one (e.g., an odds provider outage) doesn't take down injury or weather data. Recommend maintaining at least one documented fallback provider per category before launch, even if not actively integrated — this shortens the response time if a primary provider has an outage during a live NFL Sunday.

**Named vendor candidates for Phase 3 (v3.0):** the adapter pattern above means these are swappable by design, but a real default has to be picked to start building against:

| Adapter Category | Default Vendor | Fallback |
|---|---|---|
| Odds | The Odds API | (document a second before launch, per the paragraph above) |
| Player/team stats, injuries, rosters, schedules | SportsDataIO | — |
| Weather | WeatherAPI | OpenWeatherMap |
| News/sentiment | NewsAPI | GNews |

**Caching — Redis (v3.0):** the Sports Intelligence Layer caches normalized responses in Redis, sitting in front of every adapter, with category-appropriate TTLs — odds data needs near-real-time freshness (seconds), injury/roster data can tolerate minutes, weather can tolerate longer. Cached responses are shared across all users, not per-user — this is both a cost control (fewer provider calls) and a load control (protects against provider rate limits during traffic spikes), and matters most during concentrated windows like Sunday NFL slates where hundreds of users are effectively asking for the same data at once.

**Concrete refresh cadences (v3.0, revised v4.2) — replaces the previously vague "category-appropriate" language with real numbers:**

**Master Refresh vs. specialized workers — the ownership boundary (v4.4, Decision 1, 2026-08-13):** this table's original "full pull" wording for Master Refresh predates the v4.2 revision that gave Odds/Player Props/Injury their own dedicated adaptive/window-aware cadences, and read as though Master Refresh independently re-fetches those same categories every morning — exactly the duplicate-fetch problem the v4.2 adaptive-cadence work was meant to prevent. Resolved: Master Refresh owns Schedule refresh, game creation/update, season/week context, the roster/depth-chart morning refresh, `daily_game_intelligence` assembly, and travel/rest derivation where computable. It does not directly fetch Odds, Player Props, Injuries, Weather, or News — those categories remain owned by their own rows in this table. At 6 AM, Master Refresh reads whatever those workers have already persisted; if a specialized worker hasn't run yet (or doesn't exist yet, as of Phase 3E-2's build), the corresponding `daily_game_intelligence` field is left null/unavailable rather than causing Master Refresh to duplicate a provider call. See CHANGELOG.md v4.4 entry.

**Odds/Player Props Worker implementation -- shared window classification and dynamic TTL (v4.5, Phase 3E-4D/E/F, 2026-08-14):** both workers are built entirely against one shared policy module, `app.workers.windows.classify_window`, rather than each computing its own proximity-to-kickoff tiers. **CONFIRMED FROM VOLUME 2 §8** (this section, unchanged by this note): the four ramp boundaries -- 2h, 60min, 15min, 5min before kickoff -- and that polling stops entirely at kickoff. **ASSUMED** (flagged explicitly, not presented as directly confirmed Blueprint fact): this section states window *boundaries* but never a numeric polling interval *within* each window for either worker. The implementation treats each boundary as also the polling interval for the tier it opens (e.g. once inside the 2h-out window, poll every ~60 minutes -- the width down to the next boundary); the pre-first-ramp period ("1 morning snapshot" / "infrequent... days out") is operationalized as a flat 24-hour interval; the final [5min, 0) tier polls every 2 minutes, reading "every-few-minutes in the final hour" (this section's own Odds Worker wording) as meaning multiple polls in that last stretch. This interpretation is called out here for Mac's explicit confirmation, not silently treated as settled -- see `app/workers/windows.py`'s own module docstring for the identical reasoning in code.

Decision 4 (dynamic TTL) is implemented by the same module: `app.workers.windows.ttl_seconds` returns, for each window tier, the same number as that tier's poll interval -- a cached value is considered fresh for exactly as long as until the next poll for that window would occur. Both workers construct their `CachingAdapter` with this per-window TTL rather than the flat `CATEGORY_TTL_SECONDS["odds"]`/`["player_props"]` values in `app/adapters/cache.py`, which are now superseded for these two categories (kept only as dead weight for any other flat-TTL caller, of which none currently exists in-tree).

**Injury Worker implementation -- an extension of the shared window policy, not a competing one (v4.6, Phase 3E-5, 2026-08-18):** unlike Odds/Player Props, Injury Worker's real-world volatility is CONFIRMED (this section, unchanged) to be day-of-week-anchored, not purely kickoff-proximity-anchored — `classify_window`'s own tiers cannot express "more frequent Wed/Thu/Fri than Mon/Tue/Sat" since they only measure time-until-kickoff. `app.workers.windows` therefore gained `classify_injury_window`/`should_poll_injuries` (plus matching interval/TTL functions), reusing `classify_window`'s exact UTC-normalization/DST-safety discipline and `_require_aware` verbatim — the one authoritative timing module, extended rather than duplicated. Five tiers: INFREQUENT (not Wed/Thu/Fri, >2h from kickoff), ACTIVE_WEEK (Wed/Thu/Fri, >2h from kickoff), FINAL_RAMP ((90min, 2h] from kickoff, any day), INACTIVE_LIST ((0, 90min] from kickoff, any day — brackets the CONFIRMED ~90-minute inactive-list boundary), STOPPED (at/after kickoff). **CONFIRMED FROM VOLUME 2 §8:** polling stops at kickoff; "roughly once daily Wednesday-Friday" (ACTIVE_WEEK's 24h interval); the ~90-minute inactive-list boundary itself. **ASSUMED (flagged explicitly, same discipline as the Odds/Player Props ramp numbers):** which "Wednesday" a given `now` falls on is read as `now`'s UTC weekday, per this module's own pre-existing "never read local/server time" discipline; INFREQUENT's 48h interval and FINAL_RAMP/INACTIVE_LIST's 30min/15min intervals have no Blueprint-stated number and were chosen conservatively (monotonically tightening toward kickoff, mirroring the existing ramp's shape). The final pre-kickoff ramp overrides day-of-week gating on any day — the Blueprint states no day-of-week exemption for "increased polling approaching kickoff." **SportsDataIO's Injuries endpoint is one bulk call per (season, week) covering every team at once, not per-game** — structurally different from Odds/Player Props' per-game fetches. Consequently the worker's polling decision is driven by the single soonest-kickoff active game in its 7-day candidate window (the "driver game"), `last_polled_at` is a single timestamp rather than one per game, and once a poll happens every resolvable row in the response is persisted (not only the driver game's), which Decision 2's append-only, no-dedup convention (`CHANGELOG.md` v4.6 (Volume 2) entry) makes safe.

**Malformed-injury-row isolation (v4.6, Phase 3E-5, Mac's Decision 3):** `SportsDataIOInjuryAdapter.fetch_injuries`'s original 3C-ii contract wrapped its entire row-parsing loop in one try/except, so a single malformed row invalidated the whole week's response for every team. Changed explicitly for 3E-5: each row is now parsed in its own try/except, so one malformed row is logged (WARNING, with whatever identifying fields the row does carry — never fabricated) and skipped, while every other row's data survives. The provider/response-level boundary is unchanged: an HTTP failure, non-200, non-JSON body, or non-array top-level shape still fails the whole fetch — isolation only ever applies to a malformed row *within* an otherwise well-shaped response.

**Weather Worker implementation -- flat cadence, DERIVED boundary reuse, dome/indoor optimization (v4.7, Phase 3E-6, Option A, 2026-08-18):** unlike Injury, Weather's cadence is CONFIRMED flat -- this section states only "Every 15 minutes," no ramping, and no adaptive tiers were added (`app.workers.weather_worker._POLL_INTERVAL_SECONDS = 900`, matching `app.adapters.cache.CATEGORY_TTL_SECONDS["weather"]` exactly, verified before reuse). Two boundaries this section itself never states are DERIVED from conventions every other specialized worker already established, not invented fresh: the 7-day candidate window (the same `_CANDIDATE_WINDOW_DAYS` scoping decision Odds/Player Props/Injury each independently adopted) and stop-at-kickoff (reusing `app.workers.windows.classify_window`'s existing `Window.STOPPED` classification directly, never its ramp-tier intervals).

**Dome/indoor optimization, approved as part of 3E-6:** delivering it correctly required a real schema decision, since `StadiumDetails.GeoLat`/`.GeoLong`/`.Type` -- CONFIRMED present in this project's own live-captured Schedule fixture -- were being discarded during normalization (the identical gap Volume 3's v4.5 travel-semantics note already flagged for coordinates alone). Resolved as Option A (the smallest additive change, considered against a dedicated `stadiums` reference table and rejected as unnecessary scope for a ~30-venue league): `games` gains three nullable columns (Volume 3 v4.9). `games.venue_type` drives `app.workers.weather_worker.venue_is_dome`: `'dome'` -> `True` (WeatherAPI never called), `'outdoor'` -> `False` (polled normally), `'retractable_dome'` or missing -> `None` (genuinely unknown roof state -- polling may still happen if coordinates are available, since regional weather is still useful context, but the persisted `is_dome` stays `None`, never coerced to `False`). `WeatherConditions.is_dome` changed from a hard `bool = False` default to `bool | None = None`, closing a real null-not-neutral gap the original 3C-i model had. Venue coordinates (`"{lat},{long}"`) are WeatherAPI's own documented location-query form -- no geocoding vendor, no hardcoded stadium list.

**Identity, a genuine asymmetry with Odds/Player Props/Injury, not an oversight:** WeatherAPI has no native game/event concept at all -- `game_provider_ids.provider_name`'s check constraint doesn't even permit `'weatherapi'`. `WeatherConditions.game_external_id` is this project's own internal `games.id`, passed straight through by the worker; `app.persistence.weather_snapshots` deliberately does not call `resolve_game_ids`, unlike its sibling snapshot-persistence modules.

**News Worker implementation -- provider-neutral by necessity, flat cadence, a deliberate departure from Weather's stop-at-kickoff convention (v4.8, Phase 3E-7, 2026-08-18).** Two blockers were identified and stopped on before any code was written, per Mac's explicit instruction: the NewsAPI-vs-GNews provider decision (held back by Mac on 2026-08-11, never revisited -- still a **BLOCKER**, not settled by this phase) and Volume 3's continued absence of a News history table (re-confirmed by direct inspection, unchanged). Both are addressed by building against the interface, not the vendor, and by the smallest additive persistence move:

- **Provider-neutral construction.** `app.workers.news_worker` depends only on the abstract `NewsAdapter`/`NewsArticle` interface -- the same guarantee every other category's worker already relies on. `NewsAPINewsAdapter` (3C-i) is wired in only because it is the sole adapter that currently exists (no GNews code exists anywhere in this repository); swapping it for a future `GNewsNewsAdapter` requires zero change to the worker itself.
- **Flat 900-second cadence, CONFIRMED** (`app.workers.news_worker._POLL_INTERVAL_SECONDS = 900`), matching `CATEGORY_TTL_SECONDS["news"]` exactly (already correct, verified not assumed). **Unlike Weather, this worker never imports `app.workers.windows` and never stops polling a team at any game's kickoff** -- a team's news relevance (injury updates, postgame reactions, next-week previews) doesn't end when one of its games kicks off, unlike pregame odds/weather/props, so `Window.STOPPED` has no correct application here. The only boundary reused from existing convention is the 7-day candidate-game window itself (the same scoping decision every other specialized worker independently adopted), which already bounds which teams get polled at all.
- **Polling unit is a resolved `teams.id`, not a game** -- `NewsAdapter.fetch_news(team=...)` is team-scoped, so (unlike Weather/Odds/Player Props' per-game `last_polled_at`, or Injury's single bulk timestamp) this worker's natural polling entity, cache key, and `last_polled_at` key are all a `teams.id`.
- **Identity resolved by the worker, never guessed or fuzzy-matched.** `games.home_team`/`.away_team` (SportsDataIO abbreviations) resolve to `teams.id` via the existing `team_identity.resolve_team_ids` (now 32/32-confirmed for `sportsdataio`, Volume 3 v4.8), then to the canonical `teams.name` `fetch_news` expects via the new `app.persistence.teams.list_teams_by_id`. An unmapped abbreviation is excluded from that cycle (`teams_unresolved`), never guessed. This worker never issues the bare, unscoped `fetch_news(team=None)` "NFL" query at all -- its results carry no trustworthy team relationship (`related_teams=[]`), so attaching them to any specific game would be exactly the guessed relevance this project prohibits. **True league-wide news is therefore out of scope for this worker's game-keyed persistence target -- a real model/table-shape mismatch, flagged rather than silently forced.** A defensive check (`_validate_articles`) additionally confirms every returned article's own `related_teams` actually names the team it was queried for before attribution, rather than blindly trusting `NewsAPINewsAdapter`'s existing (but not universally guaranteed) contract.
- **Persistence -- Option A, Mac's approved smallest additive move.** No new table. `app.persistence.daily_game_intelligence.write_news` upserts only `game_id`/`news` (same `on_conflict`/`resolution=merge-duplicates` idiom the existing `upsert_daily_game_intelligence` uses), never touching odds/weather/injuries/etc. -- see Volume 3's unchanged §4.1 and this phase's `CHANGELOG.md` entry for the full Option A vs. B evaluation.
- **Failure/stale-data handling.** A team whose fetch fails this cycle is excluded from that cycle's results; a game depending only on that team is skipped this cycle rather than having its existing `news` value overwritten with anything empty/neutral. A team whose fetch succeeds with genuinely zero articles is written as `value: []` with a fresh timestamp -- a distinct, positive "checked, nothing" result, not the same as "not re-checked."
- **Malformed-article handling stays whole-request, a known and flagged asymmetry with Injury Worker's 3E-5 per-row isolation** -- not silently matched, since changing `NewsAPINewsAdapter`'s existing error-handling contract wasn't authorized as part of this phase.

**Pregame Worker implementation -- a coordination worker, not a new provider category (v4.9, Phase 3E-8, Decision 3, 2026-08-18).** Fetches nothing itself and owns no adapter. `app.workers.pregame_worker` triggers once a game's kickoff-proximity classification (`app.workers.windows.classify_window`) reaches `Window.RAMP_5M` -- **T-minus-5-minutes, reusing the already-CONFIRMED boundary from Odds/Player Props' own window architecture** rather than inventing a new timing concept, since this row itself states no numeric "T-minus kickoff" value. It then forces one more, unconditional pass of `app.workers.odds_worker`/`player_props_worker`/`injury_worker`/`weather_worker` for exactly that one game, via a new `target_game_ids` parameter added to each (backward-compatible -- `None` preserves every existing caller's cadence-driven behavior unchanged, proven by the full pre-existing regression suite passing unmodified). **News Worker is deliberately excluded, not overlooked:** it never stops polling a team at that team's own kickoff (v4.8's own design), so there is no "last-minute value" specific to T-minus-5 the way there is for line moves and inactive lists. **Immediately followed by a targeted `daily_game_intelligence` refresh (Decision 4)** for that one game, reusing Master Refresh's own per-game assembly logic (extracted into `app.master_refresh.game_refresh.refresh_daily_game_intelligence_for_game`, behaviorally unchanged) rather than waiting for the next 6 AM Master Refresh run -- roster/`players` composition is read back verbatim, not re-fetched, since it doesn't change in the final 5 minutes before kickoff.

**Postgame Ingestion Worker implementation -- the smaller status-scan approach, not the full event infrastructure (v4.9, Phase 3E-8, Decision 2, 2026-08-18).** No code anywhere in this codebase publishes a real Postgres LISTEN/NOTIFY event yet (confirmed before deciding this) -- `app.workers.postgame_worker` instead re-polls the same `SportsDataIOScheduleAdapter`/`app.persistence.schedule.persist_schedule_entries` Master Refresh already uses (reused, not duplicated), scoped to a backward-looking window instead of Master Refresh's forward-looking one. Structured so a future real `GameFinished` event handler can call the same ingestion function (`_ingest_final_stats_for_game`) directly, without redesigning the pipeline. **SportsDataIO's live completed-game status string is ASSUMED / DEFERRED LIVE VERIFICATION, explicitly not CONFIRMED** -- `_SCHEDULE_STATUS_MAP["Final"]` has never been observed live (the 2026 season hadn't started as of the last live capture); the remaining SportsDataIO Free Trial call was deliberately NOT spent to verify this now, since doing so before a real game has finished would likely resolve nothing -- a calendar-timing problem, not a budget one. Reuses the existing 3C-ii `SportsDataIOTeamStatsAdapter`/`SportsDataIOPlayerStatsAdapter` unchanged (built and fixture-tested, never wired into a worker until now) -- no second stats-fetch pipeline. `final_score` is derived from `TeamGameStats`' own `Score`/`HomeOrAway` fields, never a separate Scores/BoxScore endpoint.

**Status-map correction and row isolation (v4.10, 2026-08-18).** `"Final"` was upgraded to CONFIRMED FROM PROVIDER DOCUMENTATION (Mac's direct review of SportsDataIO's own docs, no live call spent). That same review surfaced a real, then-unfixed gap: `_SCHEDULE_STATUS_MAP` recognized only 2 of SportsDataIO's 9 documented statuses, so `"F/OT"` (completed overtime) never reached `"final"` at all, and any of the other 7 unmapped values -- most critically `"InProgress"`, which every live game passes through -- aborted the *entire* full-season Schedule fetch (not row-isolated), cascading to fail the whole Master Refresh or Postgame Worker run. Fixed the same day, approved by Mac: the map now covers all 9 values (`InProgress`→`live`, `F/OT`→`final`, `Postponed`→`postponed`, `Canceled`→`canceled`, `Delayed`→`scheduled`, `Suspended`→`live`, `Forfeit`→`final` -- all using the existing 5-value internal vocabulary, no schema change), and `SportsDataIOScheduleAdapter.fetch_schedule` now isolates a single malformed/unrecognized row (logged, skipped) rather than failing the whole batch -- HTTP failure and non-array top-level payloads still fail the whole call, unchanged. `"F/OT"` and `"Final"` both reach `"final"` and both trigger Postgame Ingestion identically, live-regression-tested.

**Bounded reconciliation schedule -- an APPROVED PRODUCT/ARCHITECTURE DECISION, not a SportsDataIO-confirmed requirement (Decision 5).** `initial`, `+10m`, `+30m`, `+2h`, `+24h`, `+72h`, implemented in one place (`app.workers.reconciliation`) so the intervals can change centrally without rewriting the worker. PROGRESS.md's 2026-08-10 corrections research cited a *range* from secondary-source vendor guidance ("10min-2h for the first 24h, tracked 48-72h") -- this schedule is a related but distinct, concrete policy decision, never presented as vendor-mandated.

**Idempotent, correction-aware TeamStats/PlayerStats persistence, a real design decision, not silently invented.** `team_stats`/`player_stats` have neither a uniqueness constraint nor an append-only DB trigger (Volume 3 §6 already flags this as a standing, unclosed gap). `app.persistence.team_stats`/`app.persistence.player_stats` insert a new row only when incoming stats differ from the existing latest row (by `created_at`) for that (game, team)/(game, player) pair -- reusing the same "latest row" read pattern already established elsewhere, no new schema. A DB-level append-only trigger (reusing the already-existing `block_snapshot_updates()` function) remains available future hardening, flagged, not applied.

**Player identity (Decision 1, Option B) -- solved the same way `game_provider_ids`/`team_provider_ids` were, not deferred.** `player_stats.player_id` is a hard `not null` FK, and `players` had never been populated by any existing code before this phase. `player_provider_ids` (Volume 3 v4.10) mirrors the existing two identity tables exactly. Population is fixture-backed only (`app.persistence.player_backfill.PLAYER_BACKFILL`, exactly four real captured players -- the entire evidence base this project has, no live call made or authorized to expand it); an unresolved player is reported (`unresolved_players`), never guessed by name-matching, never auto-created during ingestion.

**`daily_game_intelligence.players` reconciliation -- minimal enrichment, not a durable-table rebuild (v4.14, Phase 3F-4, Mac's approved Option A, 2026-08-19).** 3F-1 built durable `players`/`roster_memberships`/`depth_chart_snapshots`, but `daily_game_intelligence.players` kept reading straight from the in-memory `RosterEntry` list Master Refresh's own roster fetch returns -- the same object `persist_roster` separately writes durably, so within one run the two can't drift, but the working table gained no benefit from the new durable tables existing. The one real capability gap: the raw fetch only ever carries the *provider's* player id, never the internal `players.id` a Phase 4/5 consumer would need to join against `player_stats`/future postgame or recommendation systems. **Decision: enrich, don't replace.** `app.master_refresh.game_refresh._enrich_roster` adds `player_id` to each roster entry (every existing field -- team/player_external_id/player_name/position/depth_chart_rank -- unchanged); `app.master_refresh.run.run_master_refresh` resolves it via one batched `player_identity.resolve_player_ids` call for the entire slate's players (run once, after every team's `persist_roster` attempt, not per-team/per-game -- avoids N+1). A player absent from the resolved mapping (never durably ingested yet, or this cycle's `persist_roster` failed before reaching them) gets `player_id: null` -- the fresh roster/depth-chart content is still shown, never dropped, but the internal identity link is only ever present when genuinely confirmed (live-proven against real dev Supabase: a durably-linked player resolves to its real `players.id`, an unlinked one resolves to `null`, proof rows cleaned up afterward). Pregame Worker's own call site needs no change -- it already reads back whatever Master Refresh last wrote via `read_existing_players`, so the enrichment carries forward automatically.

**Exception-isolation gap, fixed (v4.15, 2026-08-19).** `app.persistence.roster_ingestion.persist_roster` calls `player_identity.ensure_player`/`resolve_player_ids` and `team_identity.resolve_team_ids`, which can raise their own exception types (`PlayerIdentityError`, `TeamIdentityError`) -- distinct from `RosterIngestionError` (raised directly by `persist_roster`'s own membership/depth-chart writes). Found during 3F-4 (confirmed by direct test execution, not just static reading, that either type previously crashed the entire `run_master_refresh` call rather than being isolated per-team the way the module's own comments describe) and reported rather than fixed, per that substep's explicit scope. **Fixed the smallest safe way in 3F-5:** `run_master_refresh`'s per-team `persist_roster` try/except now catches `(RosterIngestionError, PlayerIdentityError, TeamIdentityError)` at the exact same boundary that already isolated `RosterIngestionError` -- no generic `except Exception`, so a genuinely unrelated exception (a real programming error, not one of these three known failure modes) still propagates and fails the run loudly rather than being silently swallowed. Live-regression-tested: a `PlayerIdentityError` or `TeamIdentityError` for one team no longer blocks any other team, any other game's `daily_game_intelligence` refresh, or the run as a whole (`status` correctly becomes `"partial"`, the failed team is reported in `roster_ingestion_failures`, and its `player_id` correctly stays `null` rather than being fabricated) -- and a dedicated test proves a genuinely unrelated exception type is still allowed to surface unhandled.

**Cache metrics (v4.16, Phase 3 acceptance closure, 2026-08-19).** `app.adapters.cache.CacheMetrics` (hits/misses/sets) is owned per-`CachingAdapter` instance -- since every worker already constructs one `CachingAdapter` per category, this gives independent per-category numbers without a second category-keyed store. Exact definitions: a **hit** is `CacheBackend.get` returning non-`None`; a **miss** is `None` for any reason (new key, expired entry, or a backend read failure that fails open); a **set** is one `CacheBackend.set` *attempt* after a real fetch, not a confirmed durable write (`RedisCacheBackend.set` already swallows a write failure internally, unchanged). `hit_rate` is `hits/total`, or `None` when `total == 0` -- never a fabricated percentage from an empty or tiny sample. A separate `CacheBackend.errors` counter (only `RedisCacheBackend` ever increments it; `InMemoryCacheBackend` has no failure mode) tracks backend-level read/write failures distinctly from ordinary misses, exposed on `CachingAdapter` via a convenience `.errors` property. No redesign of the existing cache-aside architecture -- purely additive instrumentation at the one call-site (`CachingAdapter.call`) already shared by every backend.

**Full-fleet load acceptance (v4.16, Phase 3 acceptance closure, 2026-08-19).** `tests/test_load_concurrency.py` (Phase 3B, 2026-08-11) proved Sunday-slate-scale (~13 games) behavior for Odds/Player Props only, before every SportsDataIO-adapter worker and the Pregame/Postgame Workers existed. `tests/test_load_concurrency_full_fleet.py` (new) extends the same slate scale to Injury Worker (bulk endpoint stays one call), Weather Worker (per-game, bounded, one provider failure isolated), News Worker (per-distinct-team, not per-game), Master Refresh (Schedule/DepthCharts bulk stays one call each, Roster bounded to 26 distinct teams, one team's identity-write failure isolated at full-league scale), SportsDataIO TeamStats (weekly-bulk stays one call across 13 games sharing a week), and Pregame Worker (5 simultaneous T-minus-5 triggers stay bounded to exactly those 5 games' work, not a full-slate rescan). **INTERNAL PIPELINE LOAD PROVEN, not PRODUCTION PROVIDER LOAD PROVEN** -- fixtures/fakes only, same discipline as the original 3B test; says nothing about real provider throughput or rate limits (still on the DEFERRED -- FINANCIAL/EXTERNAL DEPENDENCY checklist). **A real efficiency finding surfaced, documented not fixed, out of this pass's scope:** Postgame Worker's `_ingest_final_stats_for_game` constructs a fresh `SportsDataIOTeamStatsAdapter`/`SportsDataIOPlayerStatsAdapter` per game with no shared `cache_backend` -- 5 games from the same week finalizing in the same cycle make 5 redundant identical weekly-bulk fetches instead of 1 (correctness unaffected, each game's own rows still filter correctly; only "download once, reuse everywhere" is not followed here). Flagged for a future decision, not acted on.

**Row isolation, Data Dictionary reconciliation corrective pass (v4.13, 2026-08-18).** A strict inspect-first sweep of every provider adapter (Mac's explicit "Data Dictionary reconciliation" request) found the same batch-fatal-on-one-row defect the v4.10 Schedule fix had just closed, independently present in six more places, and Mac approved a corrective pass with a priority order and one core rule: a malformed provider row must not destroy otherwise valid data from the same response or batch. `TheOddsApiOddsAdapter.fetch_odds` gained two isolation tiers (malformed event, malformed market within an otherwise-valid event); `TheOddsApiPlayerPropsAdapter.fetch_player_props` gained three (malformed per-game event, market with no usable outcomes, malformed individual outcome). `SportsDataIOTeamStatsAdapter.fetch_team_stats`/`SportsDataIOPlayerStatsAdapter.fetch_player_stats` gained two-stage isolation (filtering stage, model-building stage) because `rows` is the whole week's bulk payload shared across every game via `_WeeklyBulkCacheMixin` -- the most severe instance found, since one malformed row could previously abort the fetch for every game that week, not just the one requested. `SportsDataIORosterAdapter.fetch_roster` and `_get_depth_chart_lookup` each gained single-tier per-row isolation. Every case: the malformed unit is logged (`_logger.warning`, includes provider-identifying context) and skipped; every other valid unit in the same response still processes; HTTP failure, invalid top-level JSON, and non-array/non-object payloads still fail the whole call, unchanged. **Known characteristic of `fetch_player_props`, documented rather than silently accepted:** a malformed field that fails after a `PlayerProp` has already been inserted into the grouping dict for a given bookmaker/market/player/point key (e.g. a missing `price` on the first outcome seen for that key) leaves that prop in the result with the affected side (`over_odds`/`under_odds`) still `null`, rather than removing the entry -- consistent with the model's own optional-field design and the project's null-not-neutral convention. No schema change, no provider vocabulary expanded (`_SEASON_TYPE_MAP`/`_VENUE_TYPE_MAP`/`InjuryReport.status` left untouched -- no repo-existing provider documentation conclusively established a missing value), no live provider calls (SportsDataIO budget unchanged at 11 of 12). `player_stats_nfl`'s wiring question, surfaced by the same inspection sweep, was deliberately kept out of this pass and reported to Mac separately, per his explicit instruction.

**Odds Worker discovery mode (Phase 3E-4B/C):** `TheOddsApiOddsAdapter.fetch_odds` returns every event unfiltered when called with an empty game-id list, since the bulk `/odds` endpoint always returns the full slate regardless of filter and its CONFIRMED cost model (markets × regions) doesn't scale with event count. The Odds Worker uses this to self-discover and deterministically link (`app.persistence.odds_game_linking`, Phase 3E-4C) a game Master Refresh created that this provider hasn't been linked to yet. Player Props Worker has no equivalent, since its event-specific `/events/{id}/odds` endpoint requires already knowing the event id (CONFIRMED per-game cost model) -- **DEFERRED PRODUCTION VERIFICATION / architecture note flagged for Mac's confirmation:** Player Props Worker therefore depends on game linkage established elsewhere (the Odds Worker's own discovery pass, or any other caller of the shared linking module) and skips a due-but-unlinked game for that cycle rather than performing its own team-based discovery, to avoid duplicating a cost-relevant provider call between two independently-cadenced workers.

**Master Refresh operating horizon (v4.4, approved 2026-08-13):**

> **MASTER REFRESH OPERATING HORIZON: `[today, today + 7 days)`**

Each 6 AM run establishes game identity and assembles `daily_game_intelligence` for every game in this rolling 7-day window, not only games kicking off on the literal calendar day of the run — the purpose is to keep the near-term NFL slate prepared ahead of kickoff (a Thursday game is already prepared by the preceding Tuesday's run), not to model "today" narrowly. **This horizon governs Master Refresh's own game-identity/assembly work only — it does not change any specialized worker's cadence.** Odds/Player Props are not polled continuously for 7 days; Injuries are not polled continuously; Weather and News are not polled continuously. Each of those five categories remains governed exactly by its own row in the cadence table above, unaffected by how far ahead Master Refresh prepares game identity and working-row scaffolding. This note is the canonical statement of the horizon — it is not to be silently reinterpreted or redefined elsewhere in this document or in code.

**Why exact cadences matter enough to specify (not just "make it fast"):** the AI Transparency Meter's `data_quality` dimension (Volume 5 §5, v2.0) needs a real, calculable number — "how stale is this data right now" only means something if there's a known cadence to measure staleness against. Vague TTLs made that dimension a placeholder; concrete cadences make it real. The v4.2 revision keeps this intent but stops applying it uniformly — a 24/7 flat cadence measured staleness against a number that didn't reflect the data's actual real-world volatility, which is exactly what the adaptive/window-aware cadences above correct.

**Postgame Ingestion vs. Postgame Review — a corrected ambiguity (v4.4, Phase 3E-1 checkpoint, 2026-08-13):** an earlier revision of this section's Postgame Ingestion Worker row described that worker as making §4.4's "postgame review generation" responsibility "concrete with a name and a trigger," which read as though ingestion and review were the same worker. They are not, and are owned by different phases: **Postgame Ingestion Worker (this row, Phase 3)** detects `games.status` transitioning to final, consumes `GameFinished`, fetches/persists final score/team stats/player stats, and performs the bounded reconciliation checks described above — it does not grade recommendations, change agent weights, or produce a review. **Postgame Review generation (Phase 5, `engineering-roadmap-build-order.md` Milestone 4, `postgame_reviews` in Volume 3 §7)** is a separate, later worker that evaluates already-recommended bets against the now-final game data ingestion produced — it depends on Phase 5's recommendation architecture existing, which Phase 3 does not build. §4.4's category description above (line 115) still correctly uses "postgame review generation" as an example of the Background Workers category in general; it was only this table row's cross-reference that conflated the two, and that cross-reference is now removed.

## 9. DevOps & CI/CD

**Pipeline:** GitHub Actions → Railway, triggered on merge to environment-mapped branches (`dev` branch → dev environment, `main` → staging, tagged release → production). Every deploy runs the test suite before it's allowed to promote — no manual "just push it" deploys to production, even under time pressure, since a bad Orchestrator deploy during a live NFL Sunday is the worst-case failure mode for this specific product.

**Deploy path is single and exclusive (v4.1):** Railway's own native git-autodeploy is disabled on all three environments — `dev`, `staging`, and `production` all deploy exclusively through the Actions-gated `railway up` step above. This isn't cosmetic: running both triggers side by side produced a confirmed dual-trigger race (two live deployments for the same commit at once) and silently let untested deploys reach `dev` while the Actions pipeline's test gate ran alongside, doing nothing. `railway up` runs from the repo checkout root, not a per-service subdirectory — each service's Railway `rootDirectory` config already scopes the build, so the CI job must upload the full repo rather than a pre-scoped subfolder.

**Config-mutation safety (v4.1):** Any Railway config or variable mutation (`set-variables`, `update-service`, and equivalents) redeploys the target service by default unless told not to. On an environment with autodeploy disabled — which, per the above, is now all three — that default redeploy has no live git source to build from and falls back to replaying the last cached build snapshot, which can be stale. Standing rule (also in `CLAUDE.md`): every such mutation call passes `skipDeploys: true` unless triggering a deploy is the explicit point of that specific call.

**Secrets management:** Railway's environment variable management per-environment, never committed to the repo. Provider API keys, model API keys, and the internal service token (Section 6) are the highest-sensitivity secrets — recommend rotating model API keys on a defined schedule (quarterly) rather than only on suspected compromise.

**Observability stack:**
- **Structured logging** across all services, correlated by a request ID that follows a single recommendation from user request through agent fan-out to final response — this correlation ID is what makes the Time Machine reconstruction practical from a systems standpoint, not just a database standpoint.
- **Error tracking** (e.g., Sentry) on all services, with the Orchestrator and Sports Intelligence Layer getting the tightest alerting — these are the two services where a silent failure is most costly (a silent Sports Intel failure could feed stale odds into a live recommendation without anyone noticing). **Environment tagging (v4.1):** Sentry's SDK does not infer which Railway environment an event came from — `sentry_sdk.init()` must explicitly pass `environment=os.environ.get("RAILWAY_ENVIRONMENT_NAME", "dev")`, or every event from every environment silently defaults to being tagged `"production"`, making dev/staging noise indistinguishable from real incidents.
- **Uptime/health checks** on all services, feeding the System Health Dashboard defined in Volume 1's dashboard list.
- **Per-component latency tracking (v2.0):** attached to the same correlation ID above — recommendation end-to-end, individual agent, provider call, consensus computation, database query, and API response latency each tracked separately. This is a natural extension of tracing infrastructure that already needed to exist for Time Machine purposes, not a new system; it answers "which layer is slow" instead of just "the request was slow."

**Rollback strategy:** Railway's deployment history supports one-click rollback; the team's operating rule should be that any production incident during a live game window triggers immediate rollback to last-known-good rather than attempting a hotfix live — diagnose and fix in staging, redeploy properly afterward.

**Disaster recovery targets (v2.0):**
- **RPO (Recovery Point Objective):** no worse than the interval between automated Supabase backups — if backups run every 24 hours, that's the maximum acceptable data loss window. Verify the actual backup interval against Supabase's plan tier and tighten if the default doesn't meet this.
- **RTO (Recovery Time Objective):** scoped against the "immediate rollback during a live game window" incident protocol already established above — a code-level rollback should complete in minutes; a full data-restore scenario is the harder case and needs its own explicit target, recommended at under 4 hours for MLP stage.
- **Restore testing:** the backup restore procedure must be tested at least once before Phase 10 (Beta) in the Engineering Roadmap, not assumed to work because it's configured — an untested backup is not a real backup.

## 10. Security Touchpoints (Cross-Reference to Later Detail)

Full security architecture (RLS policies, encryption, threat modeling) belongs in Volume 3 (database-level) and gets a dedicated pass, but three decisions belong here because they're deployment-level, not schema-level:

- **Internal service token** (Section 6) is a system-architecture decision — it exists specifically so a compromised frontend-facing JWT can't be used to call internal-only endpoints directly.
- **Environment isolation** (Section 5) exists specifically so a staging/dev compromise can't touch production data or pollute the Time Machine reproducibility record.
- **AI abuse protection (v2.0):** three specific defenses, added per the external architecture review — (1) prompt injection filtering on all Natural Language Engine inputs (Volume 4 §7) before they reach any model call, since the NL Engine is the one place user-supplied free text flows directly into a model prompt; (2) rate limiting tuned specifically against SMS flooding (Twilio inbound, Volume 5 §7), distinct from and in addition to the standard tier-based API rate limits in Section 6, since SMS abuse has a different cost profile (per-message carrier cost) than API abuse; (3) circuit breakers on the Orchestrator to stop a single runaway request (e.g., a malformed retry loop) from cascading into a token-exhaustion cost or availability incident — the breaker should trip on either an elapsed-time or a call-count threshold per request, whichever is hit first.
