# The Playbook — v3.0 Amendments
## Conversational-First UX, Intelligence Pipeline, and Schema Additions

**Version:** v3.0 (MAJOR — ripples across all five volumes)
**Date:** 2026-08-05
**Trigger:** Three supplementary specification documents covering conversational AI experience, an expanded table list, and infrastructure/intelligence architecture details.
**Status of this document:** Same role as the v2.0 amendments doc — full technical detail lives here so individual volumes don't balloon with implementation detail that's really about *this* decision. Each affected volume's body gets the actual content integrated directly (learning from the v2.0.1/v2.0.2 lesson logged in `CHANGELOG.md` — header-only updates create drift, so this time the volumes themselves carry the real content, and this document is the consolidated record plus the reasoning for what was deferred).

## 1. The Real Decision: Chat-First, Not Dashboard-First

**What changes:** The default landing surface after login becomes `/chat`, not `/dashboard` (Volume 5 §3's route table). The dashboard remains fully specified as-is — it's still where recommendation history, analytics, and settings live — but it's no longer the first thing a user sees. Onboarding (Volume 1 §6 / Volume 5 §6) still ends in a live first recommendation, delivered conversationally rather than as a dashboard card.

**Why this isn't a conflict, just a reprioritization:** Volume 5 already specified a `/chat` route and the Natural Language Engine (Volume 4 §7) was always meant to understand free text like "give me something safe" or "I hate betting the Cowboys." Nothing architectural changes — every route, table, and component from v1.0/v2.0 still exists. What changes is which one a user sees first, and that the chat surface needs to carry more product weight than "one route among many" implied.

**Why accepted without asking for a tie-break:** Volume 1 §1's very first lines already say this should feel like "an elite investment firm," and the product goal stated in this new material — "should feel like texting an elite professional sports bettor" — is the same idea stated more vividly, not a different one. Adopting it doesn't reverse any prior decision; it sharpens one that was already implicit but under-specified in Volume 5.

## 2. Default Conversational Response Format

New concrete spec for how the AI responds by default (extends Volume 4 §8's Explainability Engine and Volume 5's Recommendation Card):

**Default (Level 1) response — concise, never a wall of text:**
```
🔥 Today's Favorite
Chiefs Moneyline (-135)

Confidence: 89%
Expected Value: +6.3%

The Chiefs have advantages in quarterback play, injuries, travel,
and line value. This is one of today's stronger positions.
```

**Progressive disclosure — four levels, only revealed on request:**
| Level | Trigger | Content |
|---|---|---|
| 1 | Default | One sportsbook-style card: bet, confidence, EV, 1-2 sentence summary |
| 2 | "Why?" / "Explain" | Bullet summary of the strongest 5-8 contributing factors |
| 3 | "Show me your reasoning" / "How did you get that?" | Detailed reasoning — the full explainability question set from Volume 4 §8, in prose |
| 4 | "Show me everything" / "Full report" | Complete AI consensus report — every contributing agent's output, exactly what the Explainability Panel (Volume 5 §5) already renders in full |

**Why this maps cleanly onto existing architecture:** Level 4 *is* the Explainability Panel. Level 3 *is* a prose rendering of `explainability_payloads`. Level 1 *is* the existing Recommendation Card's summary fields. Nothing new needed to be built to support this — it's a presentation-layer decision about *when* to surface data that already exists, which belongs in Volume 5, not a new data requirement for Volume 3 or Volume 4.

## 3. Parlay Generation Freedom

Extends Volume 4 §9 (Recommendation Strategy Engine): explicitly confirm that when the engine decides a parlay is appropriate, individual legs can freely mix bet types — moneyline, spread, totals, and player props (passing yards, receiving yards, anytime TD, strikeouts, points, assists, etc.) — within a single same-game or multi-game parlay. This was implicit in the original design (the Player Prop Agent already existed as a full committee member) but never stated as an explicit rule. Now explicit: **the Recommendation Strategy Engine is never restricted to one market type per parlay** — mixing markets whenever it improves expected value is the default behavior, not a special case.

## 4. Conversational Session Memory

New addition to Volume 4 §7 (Natural Language Engine): session-scoped preference tracking, distinct from the persistent `betting_dna` table (Volume 3 §3). Examples: "I don't like unders," "I only bet player props," "my bankroll today is $75" — these apply for the rest of the session without needing to be re-stated, but don't persist to `betting_dna` unless the pattern repeats across multiple sessions (that graduation path already exists via the Betting DNA background worker, Volume 3 §3).

**Schema addition:** `conversations` (Volume 4 §7) gains a `session_preferences jsonb` column:
```sql
alter table conversations add column session_preferences jsonb default '{}';
```
Populated and read by the NL Engine's intent classification step — a stated exclusion ("no unders," "no Cowboys") gets written here and checked on every subsequent recommendation request in that conversation, cleared when the conversation ends.

## 5. Kelly Criterion in the Bankroll Coach

Extends Volume 4 §2.5's Bankroll Coach agent spec: the stake suggestion is now explicitly Kelly-based rather than an unspecified "translate to a suggested stake." Fractional Kelly (recommend quarter-Kelly as the default multiplier, not full Kelly — full Kelly is too aggressive for a product whose core positioning is disciplined risk management, not maximum growth) computed from the Probability Modeling Agent's calibrated probability and the current odds, then further adjusted by the user's stated risk tolerance (`user_profiles.risk_tolerance`, Volume 3 §3) as a multiplier on top of the fractional-Kelly base. This gives the agent's existing responsibility ("how should this translate to a suggested stake") an actual formula instead of leaving it undefined.

## 6. Infrastructure: Redis Cache Layer

Extends Volume 2's service architecture: Redis added as the concrete implementation of the Sports Intelligence Layer's caching (Volume 2 §8), which previously specified *that* caching happens with category-appropriate TTLs but not *how*. Redis sits in front of the Sports Intelligence Layer's provider adapters — cached responses are shared across all users (not per-user), directly reducing provider API costs and rate-limit exposure, which matters most during concentrated traffic windows like Sunday NFL slates.

## 8. Daily Intelligence Pipeline & Worker Cadences

Extends Volume 2 §4.4 (Background Workers) with concrete schedules, replacing the previously vague "predictable load, fixed smaller instances":

| Worker | Cadence | Purpose |
|---|---|---|
| Master Refresh | Daily, 6:00 AM | Full pull: games, odds, props, injuries, weather, news, rosters, schedule updates |
| Odds Worker | Every 5 minutes | Refresh `odds_snapshots` |
| Player Props Worker | Every 5 minutes | Refresh prop markets specifically (highest volatility, highest user interest) |
| Injury Worker | Every 10 minutes | Refresh injury reports |
| Weather Worker | Every 15 minutes | Refresh weather snapshots |
| News Worker | Every 15 minutes | Refresh news/sentiment feed |
| Pregame Worker | Triggered, T-minus kickoff | Final refresh of all critical data immediately before a game starts — catches last-minute inactive lists, weather shifts, and line moves the scheduled cadences above might miss by a few minutes |

**Why this matters enough to specify exactly:** the Recommendation Pipeline's reproducibility guarantee (Volume 3's Time Machine principle) depends on knowing *how fresh* the data was at recommendation time. Vague TTLs made "data quality" (the AI Transparency Meter component, Volume 5 §5, v2.0) impossible to compute meaningfully. Concrete cadences make it a real, calculable number instead of a placeholder.

## 9. `daily_game_intelligence` Master Table

New table, extends Volume 3. This is a pre-assembled, denormalized view built by the Master Refresh worker (§8 above) each morning, combining that day's games with all currently-known intelligence into one row per game — the single place every agent looks first before querying supporting tables individually.

```sql
create table daily_game_intelligence (
  game_id uuid primary key references games(id) on delete cascade,
  teams jsonb,
  players jsonb,
  odds jsonb,
  props jsonb,
  weather jsonb,
  injuries jsonb,
  news jsonb,
  travel jsonb,
  rest jsonb,
  stadium jsonb,
  public_betting jsonb,
  sharp_money jsonb,
  ai_scores jsonb,                -- references the derived score tables below
  momentum jsonb,
  matchup_ratings jsonb,
  ev_calculations jsonb,
  confidence_scores jsonb,
  recommendation_candidates jsonb,
  last_updated timestamptz default now()
);
```

**Why this doesn't undermine the Time Machine principle (important, since it looks like it might at first glance):** `daily_game_intelligence` is a *working* table, continuously overwritten as the day's data refreshes — it is explicitly **not** a source of truth for historical reconstruction. When a recommendation is created, `recommendation_snapshots` (Volume 3 §5) still freezes a copy of everything relevant at that exact moment, same as before. `daily_game_intelligence` exists purely so agents don't have to separately query eight tables on every request — it's a performance optimization sitting *upstream* of the existing reproducibility architecture, not a replacement for it. Agents query this table first; if reconstructing history months later, the system still uses `recommendation_snapshots`, never `daily_game_intelligence`, which by then has long since been overwritten.

### Derived Intelligence Score Tables

Supporting tables that feed the `ai_scores` field above, each keyed to `game_id`, refreshed alongside the Master Refresh worker: `weather_scores`, `injury_scores`, `travel_scores`, `rest_scores`, `momentum_scores`, `matchup_scores`, `line_value_scores`, `sharp_money_scores`, `schedule_difficulty_scores`, `offensive_matchup_scores`, `defensive_matchup_scores`, `coaching_edge_scores`, `public_sentiment_scores`. Each follows the same simple shape (`game_id`, `score numeric`, `calculated_at timestamptz`) and is deliberately kept separate rather than folded directly into `daily_game_intelligence` alone, so each score's calculation can be independently tested, versioned, and — eventually — fed into the Continuous Learning Engine's evaluation of which score types actually correlate with agent accuracy (Volume 4 §10).

## 10. Human-Readable Recommendation IDs

Extends `recommendations` (Volume 3 §5):
```sql
alter table recommendations add column display_id text unique;
-- format: PB-{year}-{sport}-{sequence}, e.g. PB-2026-NFL-000234
```
Generated at creation time by a simple sequence-per-sport-per-year function. Purely a UX/support convenience — `id` (the UUID) remains the actual primary key and foreign key target everywhere; `display_id` is what a user sees and what support references when Mac or a future support person needs to look something up without pasting a UUID.

## 11. Explicitly Deferred (Not Adopted)

Consistent with the MLP-first strategy already established in v1.0/v2.0, the following from the supplementary material are **not** being adopted into the schema now:

- The bulk of the ~150-table list (doc covering sections 1–17): most either duplicate existing Volume 3 tables under different names (e.g., `profiles` = existing `user_profiles`; `bankrolls` = existing `optional_bankroll` field plus `betting_dna`; `recommendation_snapshots` already exists) or are premature for MLP scope — `training_examples`, `feature_vectors`, `model_training_runs` and the rest of "Future ML Tables" (section 16); `reddit_sentiment`, `twitter_sentiment`, `sentiment_scores` (section 5, social sentiment — genuinely interesting but no MLP-stage consumer yet, same reasoning that deferred several event types in v2.0); the extensive `historical_*` table set (section 10) where the existing append-only snapshot tables (`odds_snapshots`, etc.) already serve as the historical record by virtue of never being deleted.
- **Sportsbook promotions tracking** (profit boosts, bonus bets, odds boosts) — a real feature idea for a future release, not core to the MLP's trust-and-transparency positioning; flagged for a post-MLP business review, similar treatment to the Referral System in v2.0.
- **Social sentiment monitoring** (X, Reddit) as a full agent input — interesting, but no committee agent currently consumes it and adding a data category without a consumer repeats the mistake the v2.0 event-bus scoping was designed to avoid (infrastructure without proven consumers).

## 12. Impact on the Engineering Roadmap

**Phase 1 (Database Foundation)** gains: `daily_game_intelligence`, the derived score tables, `display_id` on `recommendations`, `session_preferences` on `conversations`.

**Phase 3 (Sports Intelligence Layer)** gains: Redis as the concrete cache layer; the named vendor candidates (§7) as defaults for each adapter; the Master Refresh worker and the specific cadence table (§8) replacing the previous vague TTL language.

**Phase 4 (AI Orchestrator)** gains: Kelly Criterion formula in the Bankroll Coach; explicit parlay market-mixing confirmation; agents now query `daily_game_intelligence` first per the ordering established in §9, falling back to supporting tables only when needed.

**Phase 5 (Recommendation Pipeline)** gains: session preference checking in the NL Engine; `display_id` generation as part of recommendation creation.

**Phase 6 (Dashboard)** — biggest re-scope: `/chat` becomes the default landing route instead of `/dashboard` (§1). The four-level progressive response format (§2) becomes part of the chat interface's core behavior, not an optional feature.

No phase needs to reopen — same as v2.0, this arrived before any phase's work began (Phase 0 covers only repo/CI/CD, none of which this touches).
