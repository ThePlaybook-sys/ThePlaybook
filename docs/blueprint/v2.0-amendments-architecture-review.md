# The Playbook — v2.0 Amendments
## Response to External Architecture Review

**Version:** v2.0 (MAJOR — ripples across Volumes 1, 2, 3, 4, 5, and the Engineering Roadmap)
**Date:** 2026-08-05
**Trigger:** External architecture review scoring the v1.0 blueprint 9.8/10 and proposing 25 improvements.
**Status of this document:** This is the detailed technical record of what was accepted, modified, or declined from that review, and the concrete schema/architecture changes that result. Each affected volume gets a short pointer section added at its end; this document holds the full specification so the volumes themselves don't balloon with implementation detail that's really about *this* decision, not the volume's core subject.

## 1. Accepted As-Proposed

### 1.1 AI Versioning (Review #3)
Extends `recommendations` (Volume 3 §5):
```sql
alter table recommendations add column ai_version text not null default 'v1';
alter table recommendations add column prompt_version text;
alter table recommendations add column agent_version text;
alter table recommendations add column consensus_version text;
alter table recommendations add column weight_version text;
```
**Why accepted without modification:** this is a direct, low-cost extension of the Time Machine principle Volume 3 already established (§1) — the blueprint already committed to "nothing is a black box," and not knowing which AI architecture version produced a given recommendation was a genuine gap, not a nice-to-have.

### 1.2 Feature Flags (Review #2)
New table:
```sql
create table feature_flags (
  id uuid primary key default gen_random_uuid(),
  flag_key text not null unique,
  description text,
  enabled boolean default false,
  audience_tier text[],                    -- e.g. ARRAY['elite']
  rollout_percentage integer default 0 check (rollout_percentage between 0 and 100),
  created_at timestamptz default now(),
  updated_at timestamptz default now()
);
```
Consumed by the Orchestrator (new consensus algorithms, experimental agents) and the frontend (beta dashboard features) alike. Read at request time, same "data not code" principle already established for `model_routing_rules` (Volume 3 §8).

### 1.3 Prompt Registry (Review #5)
```sql
create table prompt_registry (
  id uuid primary key default gen_random_uuid(),
  prompt_name text not null,
  version integer not null,
  prompt_text text not null,
  status text check (status in ('draft','active','deprecated')),
  owner text,
  updated_at timestamptz default now(),
  unique(prompt_name, version)
);
```
Every agent (Volume 4 §2) loads its prompt from this table by `(prompt_name, status='active')` rather than embedding prompt text in code. This is the mechanism that makes `prompt_version` on `recommendations` (§1.1 above) meaningful — without a registry, "prompt version" would have nothing to point to.

### 1.4 Model Registry (Review #6)
```sql
create table model_registry (
  id uuid primary key default gen_random_uuid(),
  model_name text not null unique,
  strengths text,
  weaknesses text,
  cost_per_1k_tokens numeric(10,6),
  avg_latency_ms integer,
  preferred_tasks text[],
  capabilities text[],
  status text check (status in ('active','retired')),
  updated_at timestamptz default now()
);
```
`model_routing_rules.primary_model` / `fallback_model` (Volume 3 §8) now conceptually reference `model_registry.model_name` — not a hard foreign key (routing rules should still function if a model is mid-migration), but the Orchestrator's routing decision (Volume 4 §3.2) should factor in this table's `cost_per_1k_tokens` and `avg_latency_ms` when the routing logic gets built in Phase 4, not just task-type mapping alone.

### 1.5 Cost Intelligence (Review #7)
```sql
create table recommendation_costs (
  id uuid primary key default gen_random_uuid(),
  recommendation_id uuid not null references recommendations(id) on delete cascade,
  provider text check (provider in ('openai','anthropic','ocr','sports_api')),
  cost_usd numeric(10,6),
  created_at timestamptz default now()
);
create index idx_reccosts_recommendation on recommendation_costs(recommendation_id);
```
Feeds directly into Volume 1 §8's business metrics — "average cost per recommendation," "average cost by tier" become real queries against this table joined with `subscriptions`, closing a real gap: Volume 1 committed to pricing decisions being data-driven, but the blueprint had no table to make that possible until now.

### 1.6 Expanded Audit Log (Review #22)
```sql
create table audit_log (
  id uuid primary key default gen_random_uuid(),
  actor text,                               -- 'system', a user_id, or an admin identifier
  action_type text check (action_type in
    ('prompt_change','weight_change','routing_change','model_swap',
     'consensus_change','admin_action','feature_flag_change')),
  target_id uuid,
  before_state jsonb,
  after_state jsonb,
  created_at timestamptz default now()
);
```
This is the audit trail for changes *to the system itself* — distinct from `recommendation_agent_outputs` and other tables that audit what the system *produced*. Every write to `prompt_registry`, `agents.current_weight`, `model_routing_rules`, or `feature_flags` should insert a corresponding `audit_log` row — recommend this as a database trigger, not application-layer discipline, for the same reason the append-only trigger on `recommendation_agent_outputs` (Volume 3 §11) is enforced at the database level rather than trusted to every future code path.

### 1.7 Soft Deletes (Review #11)
`deleted_at timestamptz` added to `user_profiles`, `recommendations`, `bet_slips`, and any table where a hard delete would otherwise destroy history that the Time Machine principle depends on preserving. RLS policies (Volume 3 §10) updated to filter `deleted_at is null` on standard queries, with an explicit admin-only path to query including soft-deleted rows.

### 1.8 UUIDv7 (Review #13)
Recommend switching from `gen_random_uuid()` (UUIDv4) to UUIDv7 generation specifically for the highest-insert-volume append-only tables: `odds_snapshots`, `recommendation_agent_outputs`, `market_monitoring_events`. UUIDv7's time-ordered structure improves index locality on exactly the tables that will accumulate the fastest. Lower-volume tables (subscriptions, user_profiles) can stay on standard `gen_random_uuid()` — the benefit doesn't justify the migration cost there.

### 1.9 Meta Agent (Review #8)
New 22nd agent, added to Volume 4's committee, but structurally different from the other 21 — it doesn't analyze the game, it analyzes the committee's output:

```json
{
  "agent_name": "meta_agent",
  "polarization_score": 0.0,        // how split the 21 agents were
  "uncertainty_flag": false,        // true if unusually high variance across categories
  "confidence_adjustment": 0.0,     // can only ever be negative or zero — never boosts confidence
  "reasoning": "plain-language summary of committee health for this recommendation"
}
```
Runs after the Consensus Engine (Volume 4 §4), not as part of the parallel fan-out — it needs the other 21 outputs as input. Its `confidence_adjustment` is subtracted from `aggregate_confidence` before the 0.55 "No Bet Today" threshold check (Volume 4 §4.2), and is capped at zero on the upside by design: this agent's entire purpose is catching reasons to be *more* cautious, and letting it boost confidence would create a backdoor around the anti-overfitting guardrails already built into the weighting system (Volume 4 §6).

### 1.10 Hallucination / Evidence Classification (Review #9)
Extends the shared agent output contract (Volume 4 §2.1):
```json
{
  "agent_name": "...",
  "finding": "...",
  "supporting_evidence": ["..."],
  "evidence_classification": "data_backed | inference | assumption",
  "directional_lean": "...",
  "confidence": 0.0,
  "would_change_mind_if": "..."
}
```
The Consensus Engine's weighting formula (Volume 4 §4.1) gets one addition: agents whose `evidence_classification` is `assumption` contribute at a discounted weight (recommend 0.5× their normal `current_weight` for that specific recommendation, not a permanent change to the agent's weight) — a single assumption-heavy finding shouldn't carry the same force as a data-backed one, but it also shouldn't be thrown out, since informed inference is often legitimately useful.

## 2. Accepted With Modification — Scoped Internal Event Bus (Review #1)

**The review's proposal:** full event-driven architecture connecting every major service — Orchestrator, Sports Intelligence Layer, Market Monitor, Recommendation Engine, Notification Engine, Analytics, Audit Log.

**Why not adopted as-proposed:** Volume 2 already committed the system to Railway + a small-team-appropriate operational footprint (§5), and the blueprint's own final strategic recommendation (v1.0 review, echoed by this one) is to build an MLP, not the full platform, first. A full event bus is real infrastructure — a message broker, event schema versioning, consumer group management — and introducing it everywhere on day one is exactly the kind of scope the MLP strategy exists to defer.

**What's adopted instead:** a scoped internal event system, using **Postgres LISTEN/NOTIFY** at MLP stage (no new infrastructure — Supabase already provides this) with a clear upgrade path to a dedicated broker (Redis pub/sub, or a proper queue) once volume justifies it. Wired only to the chains that were previously implied to be synchronous and would benefit most from decoupling:

**Events implemented at MLP stage:**
- `RecommendationCreated`
- `RecommendationWithdrawn`
- `RecommendationUpdated`
- `GameFinished`
- `AgentWeightsUpdated`

**Events deferred to post-MLP** (real value, but consumers don't exist yet in the MLP scope per Volume 1's phased feature list): `GameStarted`, `InjuryUpdated`, `WeatherChanged` (these matter most for the Market Monitor's own internal logic, which can stay synchronous until there are multiple independent consumers reacting to them), `UserSubscribed`, `OCRCompleted` (both tied to features — billing automation, OCR — that are themselves post-MLP or early-MLP-adjacent per the roadmap).

**Direct benefit realized immediately:** `RecommendationCreated`, `RecommendationUpdated`, and `RecommendationWithdrawn` events are exactly what powers the **Recommendation Timeline** UI component (Section 4 below) — this is a case where the scoped event system pays for itself in a specific, already-planned feature rather than existing as pure infrastructure investment.

## 3. Accepted, Volume 2 Additions

### 3.1 AI Abuse Protection (Review #21)
Added to Volume 2's security section (§10): prompt injection filtering on all Natural Language Engine inputs (Volume 4 §7) before they reach any model call; reinforced rate limiting specifically tuned against SMS flooding (Twilio inbound, Volume 5 §7) distinct from normal API rate limits; circuit breakers on the Orchestrator to prevent token exhaustion from a single runaway request (e.g., a malformed retry loop) from cascading into a cost or availability incident.

### 3.2 Disaster Recovery (Review #14)
Added to Volume 2 §9: define RTO (Recovery Time Objective) and RPO (Recovery Point Objective) explicitly before Phase 11 — recommend RPO no worse than the interval between automated Supabase backups, and RTO scoped against the "immediate rollback during a live game window" incident protocol already established. Backup restore procedure should be tested at least once before Phase 10 (Beta), not assumed to work because it's configured.

### 3.3 Expanded Observability (Review #15)
Added to Volume 2 §9: per-component latency tracking (recommendation end-to-end, individual agent, provider call, consensus computation, database query, API response) attached to the same correlation ID already used for Time Machine tracing — this is a natural extension of tracing infrastructure that already needed to exist, not a new system.

## 4. Accepted, Volume 5 Additions

### 4.1 AI Transparency Meter (Review #16)
New display treatment for the Explainability Panel (Volume 5 §5), showing four dimensions instead of confidence alone: **Confidence** (existing), **Evidence Strength** (derived from the `evidence_classification` field, §1.10 above — what % of contributing findings were data-backed vs. inference vs. assumption), **Agent Agreement** (derived from `agreement_variance`, Volume 4 §4.1), **Data Quality** (derived from Sports Intelligence Layer cache freshness at recommendation time — was this built on live data or a slightly stale cache).

### 4.2 Recommendation Timeline (Review #17)
New component, powered directly by the scoped event system (Section 2 above):
```typescript
type RecommendationTimelineProps = {
  recommendation_id: string;
  events: { event_type: string; timestamp: string; detail: string }[];
};
```
Populated by querying events tied to a `recommendation_id` — at MLP stage this means `RecommendationCreated`, `RecommendationUpdated`, and `RecommendationWithdrawn` only, matching the scoped event list in Section 2. This is a good example of the review's ideas compounding well together: the event system (#1) and this timeline (#17) were proposed as separate items but are really one feature.

## 5. Accepted, Volume 1 Additions

### 5.1 Referral System (Review #19)
Flagged as a near-term post-launch lever, not an MLP requirement — add a `referral_code` field to `user_profiles` now (cheap, avoids a later migration) but defer the actual referral program mechanics until real Persona A retention data exists to design the incentive around, per Volume 1 §7's Journey 2 finding that this persona is the natural word-of-mouth engine.

### 5.2 Public Transparency Portal (Review #20)
Strong alignment with the core "trust over win-rate" philosophy (Volume 1 §1) and explicitly flagged as a **post-MLP** feature — it requires aggregate public-facing reporting infrastructure that doesn't exist yet and depends on having enough real settled recommendations to be credible rather than sparse. Recommend targeting this for the first major post-launch release after Phase 11, not before.

## 6. Declined / Deferred Without Modification

- **Knowledge Graph (#10):** Deferred, no near-term implementation. Real long-term value for relationship discovery (player-team-coach-stadium-weather-officiating chains) but it's a new category of infrastructure (graph database or graph-modeled relational extension) without a proven MLP-stage need — the existing relational schema plus `jsonb` fields already support everything the agent committee needs for launch.
- **AI Notebook (#18):** Declined as a new backend concept — functionally, this already exists as the combination of `recommendation_snapshots`, `explainability_payloads`, and `postgame_reviews` (Volume 3 §5, §7). If a unified "notebook" view is wanted, it belongs in Volume 5 as a UI aggregation of existing data, not a new table or engine.
- **Plugin Architecture for future sports (#23):** Not declined, but not a near-term action either — the Sports Intelligence Layer's adapter pattern (Volume 2 §8) already generalizes this way by design. No schema change needed now; worth revisiting explicitly when NBA/MLB (Volume 1's stated future sports) actually enters planning.
- **Marketplace (#24):** Long-term vision only, no architectural action at this stage.
- **Architecture Decision Records (#25):** Declined as a parallel system — `CHANGELOG.md`'s four-field format (reason, decision, alternatives, impact) already functions as a lightweight ADR log for this project. Introducing a separate ADR folder would duplicate it without adding information.

## 7. Impact on the Engineering Roadmap

**Phase 1 (Database Foundation)** must now include, before its acceptance criteria (previously defined) are considered met: `feature_flags`, `prompt_registry`, `model_registry`, `recommendation_costs`, expanded `audit_log`, soft-delete columns, UUIDv7 on the three high-volume tables named in §1.8, and the AI versioning columns on `recommendations`.

**Phase 4 (AI Orchestrator)** must now include the Meta Agent (§1.9) as part of "all agents built" — the committee is now 22 members, not 21, though only 21 participate in the parallel fan-out.

**Phase 5 (Recommendation Pipeline)** must wire `RecommendationCreated`/`Updated`/`Withdrawn` events (§2) as part of the same transaction that writes to `recommendation_snapshots` — same non-negotiable reliability requirement already established for the snapshot write itself.

**Phase 6 (Dashboard)** must include the AI Transparency Meter and Recommendation Timeline components (§4) as part of the Explainability Panel work already scoped.

No phase needs to be reopened — this review arrived before any phase started building, which is exactly the scenario the blueprint's "no code before the blueprint is complete" rule (master spec) and this document's own versioning discipline were designed to catch changes in time for.
