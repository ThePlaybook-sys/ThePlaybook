# Secrets Management

Implements Volume 2 §9 (DevOps & CI/CD) and CLAUDE.md's Credentials & Connections section.

## Where secrets live

- **Runtime secrets** (model API keys, provider keys, Twilio, Supabase service role key, internal service token) are set as Railway environment variables, scoped per environment (`dev`, `staging`, `production`). Each environment gets its own values — a `dev` key is never reused in `production`.
- **CI/CD-time secrets** (`RAILWAY_TOKEN`, used by `.github/workflows/ci-cd.yml` to deploy) are set as GitHub Actions secrets, scoped per GitHub Environment (`dev`, `staging`, `production`) matching the branch-to-environment mapping in Volume 2 §9.
- Nothing in either category is ever committed to the repo. `.env` and `.env.local` are gitignored at the repo root for local development use only, and local `.env` values are never the source of truth for a deployed environment — Railway's environment variables are.

## Who can create/rotate what

Per CLAUDE.md: API keys and provider credentials cannot be generated by Claude Code. Mac creates each one on the provider's own dashboard, then provides it once so it can be set as a Railway/GitHub environment variable — never hardcoded, never echoed back in full after being set.

## Internal service token (Phase 2)

Implements Volume 2 §6/§10 — service-to-service calls (e.g., Orchestrator/Workers' internal-only endpoints) use this token, never a user JWT, so a compromised frontend-facing JWT can't be used to reach internal-only endpoints directly.

**Generation:** a cryptographically random token per environment (`secrets.token_hex(32)`, 64 hex characters), generated independently for `dev`, `staging`, and `production` — never the same value reused across environments. Set as `INTERNAL_SERVICE_TOKEN` on every service in the internal mesh (`api-gateway`, `ai-orchestrator`, `sports-intel-layer`, `worker-scheduled`, `worker-market-monitor`) within that environment, using `skipDeploys: true` per the standing Railway config-mutation rule. Never set on `frontend` — the internal token must never reach client-facing code.

**Rotation procedure (manual — automated rotation deferred to a later phase):**
1. Generate a new token for the target environment only (`python3 -c "import secrets; print(secrets.token_hex(32))"` or equivalent).
2. Set the new value as `INTERNAL_SERVICE_TOKEN` on every service in that environment's internal mesh, in the same Railway config-mutation call pattern used originally (`skipDeploys: true` unless a deploy is separately intended) — all services in that environment must be updated together, since they all must agree on the same current value at once. There is no overlap/dual-token window in the current design: rotating means a brief window where in-flight internal calls using the old token will 401 until every service has the new value, which is acceptable given Phase 2's internal endpoints aren't yet load-bearing production traffic.
3. Verify via `list-variables` that the new value is present on every service in that environment (never verify by echoing the value back in full — confirm presence, not content).
4. Confirm no accidental redeploy occurred (`get-status` timestamps unchanged) if `skipDeploys: true` was intended.
5. Update this file's inventory table's "last rotated" context in the same change (add a dated note here if this procedure is ever executed for real).
6. Never rotate `dev`'s, `staging`'s, and `production`'s tokens to the same value, and never copy one environment's token into another's Railway config as a shortcut.

## Adding a new secret

1. Mac generates it on the provider's dashboard.
2. Claude Code (or Mac directly) sets it as a Railway environment variable on the specific service(s) and environment(s) that need it — never all services by default, matching least-privilege.
3. If the secret is needed at CI/CD deploy time rather than runtime, it goes into GitHub Actions environment secrets instead (or in addition).
4. Update the inventory table above in the same change.

## Rollback note

Rotating or revoking a secret is not the same operation as a code rollback (Volume 2 §9's incident protocol). If a live incident is credential-related (a leaked key), revoke/rotate the credential first, then decide separately whether a code rollback is also needed.
