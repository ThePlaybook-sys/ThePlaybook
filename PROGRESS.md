  1. **Builder misconfiguration.** All deployments failed with "Detected Python / Using pip / No start command detected." Root cause: Railway's `dockerfilePath` setting alone is not sufficient — the separate `build.builder` field must be explicitly set to `DOCKERFILE`, or Railway silently defaults to Railpack auto-detection regardless of `dockerfilePath`. Fixed directly on all 6 Railway services in both environments (Railway-side config, not a repo change).
  2. **Frontend CVE block.** `next@14.2.15` carried two HIGH-severity CVEs (CVE-2025-55184, CVE-2025-67779); Railway's dependency scanner refused to build until patched. Fixed in PR #1: bumped to `next@14.2.35`.
  3. **Healthcheck failures post-build.** Once the builder fix took effect, all 4 Python services' Dockerfiles still failed their `/health` checks — they hardcoded `--port 8000` instead of reading Railway's injected `$PORT`, so Railway's healthcheck (which always probes `$PORT`) timed out. Fixed in PR #1: `CMD ["sh","-c","uvicorn app.main:app --host 0.0.0.0 --port ${PORT:-8000}"]` in all 4 Python Dockerfiles.
  - PR #1 (`claude/playbook-phase0-railway-h5ohzr` → `dev`) merged 2026-08-06; CI green (5/5 test jobs); merge auto-triggered fresh deploys. All 12 dev+staging deployments confirmed `SUCCESS` via both the Railway API and the dashboard.

- **2026-08-07 — `RAILWAY_TOKEN` is set and deploy jobs now actually run — and they're broken.** `RAILWAY_TOKEN` was set as a GitHub Actions environment secret earlier in the session (superseding the "still not set" note below, kept for history). This was the first time `ci-cd.yml`'s deploy jobs ran for real rather than being skipped, and re-running the earlier stuck dev-branch push (commit `5cc05a4`) surfaced two independent, previously-invisible defects — masked until now because dev/staging deploys had been happening via Railway's own GitHub auto-deploy, not the Actions pipeline:
  1. **`deploy-dev (workers)` fails outright: `Service not found`.** The matrix uses `workers` as the Railway `--service` name, but no Railway service is named `workers` — the codebase at `apps/workers` deploys as two separate Railway services, `worker-scheduled` and `worker-market-monitor`. Neither name matches the matrix entry.
  2. **The other 4 deploy jobs (`api-gateway`, `ai-orchestrator`, `sports-intel-layer`, `frontend`) report `success` in GitHub Actions but the Railway deployment they trigger actually fails.** `railway up --detach` only confirms the deploy was *triggered*, not that it *succeeded* — the Actions job exits 0 immediately without waiting for the build. Checked directly against the Railway API: all 4 resulting deployments show `status: FAILED`. Root cause (from `api-gateway`'s build log): `railway up` runs with `working-directory: apps/<service>`, uploading only that subfolder as the build snapshot — but each Railway service's `rootDirectory` is configured as `apps/<service>` (correct for git-push-triggered deploys, which upload the whole repo), so the builder then tries to resolve `apps/<service>` *inside* a snapshot that's already scoped to just that folder, and fails: `lstat .../apps: no such file or directory`.
  - **Net effect:** the CI-gates-deploy path has never actually worked end-to-end for any service via GitHub Actions — Phase 0's "trivial change pushed to `dev` deploys automatically" acceptance criterion has only ever been satisfied by Railway's native autodeploy, not by the Actions pipeline that's supposed to gate it on tests passing. This is a genuine defect per CLAUDE.md's blueprint-vs-reality process, flagged here rather than silently patched — proposed fix (not yet applied, pending Mac's confirmation): drop the `working-directory: apps/${{ matrix.service }}` from the deploy steps so `railway up` uploads the full repo and lets each service's configured `rootDirectory` do the scoping (matching how autodeploy already works correctly), and split the `workers` matrix entry into `worker-scheduled` and `worker-market-monitor` so both real Railway services get deployed.
  - Dev environment impact: each service's *previous* successful deployment is still what's serving live traffic — Railway doesn't take a service down just because a new deploy attempt failed — so this was a pipeline defect, not a live outage.
- "Wait for CI" / "disable autodeploy" toggles are dashboard-only settings, not exposed via the Railway MCP tools available in this session — needed so a failing test actually blocks a dev/staging deploy per Phase 0's testing requirements. Not yet configured; will need Mac to set these in the Railway dashboard, or a fallback approach flagged if that turns out to be blocking.
